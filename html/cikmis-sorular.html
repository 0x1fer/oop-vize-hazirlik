1.2Soru 2 – Stable Intermediate Forms

Soru 2

Stable intermediate forms nelerdir? Açıklayınız.

Çözüm

Complex systems evolve much faster and more safely if they pass through stable intermediate forms. At every step we have a stable, working form; if a change fails we return to the last stable form instead of starting again. This minimizes the effects of the moving target problem and of inevitable mistakes. Three ways:

  1. Three points of contact: Like a climber who keeps three limbs fixed and moves only one, we change only one thing at a time and keep everything else stable. When the change is tested and stable, we change the next thing. If the change has a negative effect, it is easy to go back, and we know which change caused the problem.
  2. Copy before release: Before a new version is released (before the change goes live), a copy/backup of the current stable version is taken, so that we can roll back if the new version fails (baselines, version control).
  3. Iterative and incremental software development: The product is built in increments (mini projects) and the workflows are iterated in each increment. At the end of each increment there is a working but incomplete product, i.e. a stable intermediate form. We start with the most important core (stepwise refinement, Miller's law) and grow it like a snowball (snowball effect); risks are reduced and the product evolves with new information.

Karmaşık sistemler, kararlı ara formlardan (stable intermediate forms) geçerek gelişirlerse çok daha hızlı ve güvenli gelişir. Her adımda kararlı, çalışan bir form vardır; bir değişiklik başarısız olursa her şeye baştan başlamak yerine son kararlı forma geri dönülür. Bu, moving target probleminin ve kaçınılmaz hataların etkisini azaltır. Üç yolu vardır:

  1. Three points of contact (üç temas noktası): Üç uzvunu sabit tutup yalnızca birini hareket ettiren bir tırmanıcı gibi, aynı anda yalnızca tek bir şeyi değiştirir, diğer her şeyi sabit tutarız. Değişiklik test edilip kararlı hâle gelince sıradakini değiştiririz. Değişiklik olumsuz sonuç verirse geri dönmek kolaydır ve sorunun hangi değişiklikten çıktığını biliriz.
  2. Copy before release (yayından önce kopyala): Yeni bir sürüm yayımlanmadan (değişiklik canlıya alınmadan) önce mevcut kararlı sürümün kopyası/yedeği alınır; yeni sürüm başarısız olursa kararlı kopyaya geri dönülür (baseline, sürüm kontrolü).
  3. Iterative and incremental software development (yinelemeli ve artırımlı geliştirme): Ürün artırımlar (mini projeler) hâlinde geliştirilir ve her artırımda iş akışları yinelenir. Her artırımın sonunda çalışan ama eksik bir ürün, yani kararlı bir ara form vardır. En önemli çekirdekten başlanır (stepwise refinement, Miller yasası) ve ürün kartopu gibi büyütülür (snowball effect); riskler azalır, ürün yeni bilgilerle evrilir.

1.3Soru 3 – Cohesion / coupling türü ve düzeltilmesi

Soru 3 (yeniden kurulmuş kod)

Aşağıdaki modüllerin cohesion türlerini, modüller arasındaki coupling türünü bulunuz ve kodu daha iyi cohesion ve coupling'e sahip olacak şekilde yeniden yazınız.

class Banka
{
    public static double toplamTutar;           // global veri
    public void kdvekle_indirimuygula(int indirimOrani)
    {
        toplamTutar = toplamTutar - toplamTutar * indirimOrani / 100.0;
        toplamTutar = toplamTutar + toplamTutar * 0.20;
    }
    public void Islemler(Musteri m, double faizOrani)
    {
        double faiz = faizOrani / 100;
        Console.WriteLine("Hos geldiniz " + m.Ad);
        m.Bakiye = m.Bakiye + m.Bakiye * faiz;
        LogDosyasiniAc();
    }
}
Çözüm

a) kdvekle_indirimuygula: communicational cohesion. The method performs two actions (applying the discount and adding VAT). They are related by the procedure of the product (first discount, then VAT) and both operate on the same data (toplamTutar), so it has communicational cohesion.Metot iki eylem yapıyor (indirim uygulama ve KDV ekleme). Bu eylemler ürünün prosedürüyle ilişkili (önce indirim, sonra KDV) ve ikisi de aynı veri (toplamTutar) üzerinde çalışıyor; bu yüzden communicational cohesion'a sahiptir. Öğrenciler procedural, logical, temporal da yazdı; “aynı veri” ölçütü communicational'a götürür. Gerekçeyi yazmak puanı kurtarır.

b) Islemler: coincidental cohesion. Faiz hesaplama, karşılama mesajı yazdırma ve log dosyası açma birbiriyle ilgisiz işlerdir; aynı metotta olmaları tesadüftür. (Hepsi oturum başlangıcında art arda yapılıyorsa temporal demek de savunulabilir; hoca benzer örnekte “coincidental ya da temporal” dedi.)

c) Coupling:

  • toplamTutar public static: bu alanı yazan her modül ile kdvekle_indirimuygula arasında common coupling vardır.
  • Islemler'e bütün Musteri nesnesi gönderiliyor ama sadece Ad ve Bakiye kullanılıyor ⇒ çağıran ile Islemler arasında stamp coupling.

d) Düzeltilmiş kod: her metot tek iş yapar (functional), veri gizlenir ve işlemleriyle aynı sınıfta durur (informational), parametreler basit veri (data coupling).

class Sepet                                   // informational cohesion
{
    private double toplamTutar;               // information hiding, global yok
    public Sepet(double tutar) { toplamTutar = tutar; }
    public void IndirimUygula(int indirimOrani)          // functional
    { toplamTutar -= toplamTutar * indirimOrani / 100.0; }
    public void KdvEkle(double kdvOrani)                 // functional
    { toplamTutar += toplamTutar * kdvOrani; }
    public double Tutar() { return toplamTutar; }
}

class Hesap
{
    private double bakiye;
    public void FaizEkle(double faizOrani)               // functional, data coupling
    { bakiye += bakiye * faizOrani / 100; }
}

class Ekran   { public void Karsila(string ad) { Console.WriteLine("Hos geldiniz " + ad); } }
class Logger  { public void DosyayiAc() { /* ... */ } }

After refactoring each method has functional cohesion, each class has informational cohesion, and all modules are data coupled (only simple data is passed, no global data).Yeniden düzenlemeden sonra her metot functional cohesion'a, her sınıf informational cohesion'a sahiptir ve bütün modüller data coupled'dır (yalnızca basit veri gönderilir, global veri yoktur).

{
    private int ilk, son;

5.1Soru 1 – Unified Process (15 p)

Soru 1

Unified Process nedir? Fazlarını ve iş akışlarını açıklayınız.

Çözüm

The Unified Process is an object-oriented software development methodology published by Booch, Jacobson and Rumbaugh (1999). It is not a series of steps; it is an adaptable methodology modified for each product. It is a modeling technique that uses UML, and it is iterative, incremental and two-dimensional (workflows = technical context, phases = business context).

Workflows:

  • Requirements: determine the client's needs: understand the domain, build the business model, determine the constraints (deadline, parallel running, portability, reliability, response time, cost).
  • Analysis: analyze and refine the requirements in a precise language for the designers; specification document; after sign-off, the SPMP (cost and duration estimates, deliverables, milestones, budget).
  • Design: refine the analysis until it can be implemented; architectural design (modules/classes) and detailed design (data structures, algorithms); choose language, reuse, portability.
  • Implementation: implement the product in the chosen language (subsystems, components).
  • Test: responsibility of every developer and the SQA group; traceability; reviews; unit, integration, product and acceptance testing; alpha and beta releases.

Phases:

  • Inception: is the product economically viable? Understand the domain, build the business model, delimit the scope, initial business case; identify the three risk categories (technical, requirements, architecture). Deliverables: initial domain/business/requirements models, initial risk list, plan for elaboration, initial business case.
  • Elaboration: refine the requirements and architecture, monitor risks, refine the business case, produce the project management plan.
  • Construction: produce the first operational-quality version (beta release); emphasis on implementation and testing; user manuals.
  • Transition: ensure the client's requirements are met; correct faults, complete the manuals, discover unidentified risks; driven by feedback from beta sites.

Unified Process, Booch, Jacobson ve Rumbaugh'un 1999'da yayımladığı nesne yönelimli bir yazılım geliştirme metodolojisidir. Bir adımlar dizisi değildir; her ürüne göre değiştirilen uyarlanabilir bir metodolojidir. UML kullanan bir modelleme tekniğidir; yinelemeli, artırımlı ve iki boyutludur (iş akışları = teknik bağlam, fazlar = iş bağlamı).

İş akışları (workflows):

  • Requirements: müşterinin ihtiyaçlarını belirle: alanı anla, iş modelini kur, kısıtları belirle (teslim tarihi, paralel çalışma, taşınabilirlik, güvenilirlik, yanıt süresi, maliyet).
  • Analysis: gereksinimleri tasarımcılar için kesin bir dille analiz et ve incelt; specification document; müşteri onayından sonra SPMP (maliyet ve süre kestirimi, teslim edilecekler, kilometre taşları, bütçe).
  • Design: analizi gerçekleştirilebilir hâle gelene kadar incelt; mimari tasarım (modüller/sınıflar) ve ayrıntılı tasarım (veri yapıları, algoritmalar); dil seçimi, yeniden kullanım, taşınabilirlik.
  • Implementation: ürünü seçilen dilde gerçekleştir (alt sistemler, bileşenler).
  • Test: her geliştiricinin ve SQA grubunun sorumluluğu; izlenebilirlik; gözden geçirmeler; unit, integration, product ve acceptance testleri; alfa ve beta sürümleri.

Fazlar (phases):

  • Inception: ürün ekonomik olarak yapılabilir mi? Alanı anla, iş modelini kur, kapsamı daralt, ilk business case; üç risk kategorisini belirle (teknik, gereksinim, mimari). Çıktılar: ilk domain/business/requirements modelleri, ilk risk listesi, elaboration planı, ilk business case.
  • Elaboration: gereksinimleri ve mimariyi incelt, riskleri izle, business case'i incelt, proje yönetim planını hazırla.
  • Construction: ilk işletme kalitesindeki sürümü (beta release) üret; ağırlık gerçekleştirme ve testte; kullanıcı kılavuzları.
  • Transition: müşterinin gereksinimlerinin karşılandığından emin ol; hataları düzelt, kılavuzları tamamla, fark edilmemiş riskleri bul; beta sitelerinden gelen geri bildirimle yürür.

5.3Soru 3 – Cohesion ve coupling (15 p)

Soru 3

Kohezyon ve coupling'i açıklayınız. Türlerinin başlıklarını yazınız.

Çözüm

Cohesion is the degree of interaction within a module; coupling is the degree of interaction between two modules. A good design has maximal interaction within a module (high cohesion) and minimal interaction between modules (low coupling); this makes maintenance easier and reduces regression faults.Cohesion bir modülün içindeki etkileşimin derecesidir; coupling iki modül arasındaki etkileşimin derecesidir. İyi bir tasarımda modül içi etkileşim en yüksek (high cohesion), modüller arası etkileşim en düşüktür (low coupling); bu bakımı kolaylaştırır ve regression fault'ları azaltır.

Cohesion (kötüden iyiye)Coupling (kötüden iyiye)
1. Coincidental1. Content
2. Logical2. Common
3. Temporal3. Control
4. Procedural4. Stamp
5. Communicational5. Data
6. Functional
7. Informational

Her seviyeye birer cümlelik tanım eklemek puanı garantiler:

  • Coincidental: the module performs multiple, completely unrelated actions.
  • Logical: the module performs a series of related actions, one of which is selected by the calling module (control flag).
  • Temporal: the module performs a series of actions related in time (e.g. initialization).
  • Procedural: the module performs a series of actions related by the procedure to be followed by the product.
  • Communicational: the actions are related by the procedure and all of them are performed on the same data.
  • Functional: the module performs exactly one action (achieves a single goal).
  • Informational: the module performs a number of actions, each with its own entry point and independent code, all on the same data structure (ADT, class).
  • Content coupling: one module directly references the contents of the other (modifies its local data or code, branches into it).
  • Common coupling: both modules have access to the same global data.
  • Control coupling: one module passes an element of control (flag, code) to the other, which decides what the other does.
  • Stamp coupling: a data structure is passed as an argument, but the called module operates on only some of its components.
  • Data coupling: every argument is either a simple argument or a data structure in which all elements are used by the called module.
  • Coincidental: modül birbiriyle tamamen ilgisiz birden çok eylem yapar.
  • Logical: modül birbiriyle ilgili bir dizi eylem yapar; hangisinin çalışacağını çağıran modül seçer (kontrol bayrağı).
  • Temporal: modül zaman bakımından ilişkili bir dizi eylem yapar (ör. başlangıç işlemleri).
  • Procedural: eylemler ürünün izlediği prosedürle (iş akışındaki sırayla) ilişkilidir.
  • Communicational: eylemler prosedürle ilişkilidir ve hepsi aynı veri üzerinde yapılır.
  • Functional: modül tam olarak tek bir eylem yapar (tek bir amaca ulaşır).
  • Informational: modül her biri kendi giriş noktasına ve bağımsız koduna sahip birden çok eylem yapar; hepsi aynı veri yapısı üzerindedir (ADT, sınıf).
  • Content coupling: bir modül diğerinin içeriğine doğrudan başvurur (yerel verisini/kodunu değiştirir, içine dallanır).
  • Common coupling: iki modül de aynı global veriye erişir.
  • Control coupling: bir modül diğerine onun ne yapacağını belirleyen bir kontrol öğesi (bayrak, kod) gönderir.
  • Stamp coupling: parametre olarak bir veri yapısı gönderilir ama çağrılan modül yalnızca bir kısmını kullanır.
  • Data coupling: her parametre ya basit veridir ya da bütün elemanları çağrılan modülce kullanılan bir veri yapısıdır.

6.1Sınıflar arası ilişki türleri

Kaynak

Soru

Aşağıdaki sınıf ilişkilerini açıklayınız, gösterimlerini çiziniz: a) Association (unary ve binary) b) Inheritance c) Realization d) Dependency e) Aggregation f) Composition.

Çözüm
  • a) Association Unary: class A knows about class B but B knows nothing about A; drawn as a line with an open arrowhead pointing to B (the called class). Binary: A knows about B and B knows about A (they call each other's methods); drawn as a plain solid line.
  • b) Inheritance (generalization) “is-a”: the subclass inherits the attributes and operations of the superclass; solid line with a hollow triangle pointing to the superclass.
  • c) Realization A class implements an interface (“can-do”); the interface contains only method names and parameters. Dashed line with a hollow triangle pointing to the interface. (Not: öğrenci cevabında “içi dolu ok” yazıyor; bazı çizim araçları üçgeni renkli doldurur ama UML standardında üçgen boştur.)
  • d) Dependency “uses-a”: when the definition of one element changes, the other may be affected (parameter, local variable); dashed line with an open arrowhead.
  • e) Aggregation “has-a” / collection–member; the part can exist without the whole; hollow diamond on the whole (collection) side.
  • f) Composition The strongest relationship; part–whole with lifetime control, the part cannot exist without the whole; filled diamond on the whole side.
  • a) Association Unary (tek yönlü): A sınıfı B'yi bilir ama B, A'dan habersizdir; B'ye (çağrılan sınıfa) bakan açık uçlu okla çizilir. Binary (çift yönlü): A, B'yi; B de A'yı bilir (birbirlerinin metotlarını çağırırlar); düz çizgiyle çizilir.
  • b) Inheritance (generalization) “is-a” (bir ... dır): alt sınıf üst sınıfın nitelik ve işlemlerini miras alır; üst sınıfa bakan boş üçgenli düz çizgi.
  • c) Realization Bir sınıfın bir arayüzü gerçekleştirmesi (“can-do”); arayüz yalnızca metot adlarını ve parametrelerini içerir. Arayüze bakan kesikli çizgi ve boş üçgen. (Not: öğrenci cevabında “içi dolu ok” yazıyor; bazı çizim araçları üçgeni renkli doldurur ama UML standardında üçgen boştur.)
  • d) Dependency “uses-a” (kullanır): bir öğenin tanımı değişince diğeri etkilenebilir (parametre, yerel değişken); kesikli çizgi ve açık uçlu ok.
  • e) Aggregation “has-a” / topluluk–üye; parça bütün olmadan da var olabilir; bütün (topluluk) tarafında boş elmas.
  • f) Composition En güçlü ilişki; yaşam döngüsü kontrolü olan parça–bütün ilişkisi, parça bütün olmadan var olamaz; bütün tarafında dolu elmas.

Gösterimler:

Elmas her zaman bütünün (collection/whole) yanına çizilir; kalıtım üçgeni ata sınıfa, directed association oku çağrılan sınıfa bakar.

C# karşılıkları:

class A { B myB; public void DoSomething() { myB.Service(); } }   // binary association:
class B { A myA; public void Operation()   { myA.DoSomething(); } } //   ikisi de birbirini cagirir

class C { B myB; public void Do() { myB.Service(); } }   // unary association: C -> B

class Takim { List<Oyuncu> oyuncular;                    // aggregation:
              public void Ekle(Oyuncu o) { oyuncular.Add(o); } } // oyuncu disarida yaratilir

class Ev { List<Oda> odalar = new List<Oda>();           // composition:
           public Ev() { odalar.Add(new Oda()); } }      // parcayi butun yaratir ve yok eder

class Gul : Cicek { }                                    // inheritance (is-a)
interface IUcabilir { void Uc(); }
class Kus : IUcabilir { public void Uc() { } }           // realization (can-do)
class Rapor { public void Bas(Yazici y) { y.Yaz(); } }   // dependency (uses-a)

Elaboration, construction ve transition fazlarını açıklayınız.

Çözüm

Elaboration: başlangıç çıktılarını incelt (gereksinimler, mimari), riskleri izle, business case'i incelt, project management plan'ı hazırla. Construction: ilk işletme kalitesinde sürüm (beta); implementation, unit/integration/product testing; kullanıcı kılavuzları. Transition: müşteri gereksinimleri karşılanıyor mu, hatalar düzeltilir, kılavuzlar tamamlanır, yeni riskler aranır.

K10

İki boyutlu modele neden ihtiyaç duyulur?

Çözüm

Gerçek projeler tek seferde tamamlanamayacak kadar büyüktür; Miller kuralı gereği artırımlara (fazlara) bölünür ve her artırımda iş akışları yinelenir. İki boyutlu model hem iş akışlarını (teknik bağlam) hem fazları (iş bağlamı) gösterir; moving target ve kaçınılmaz hatalarla daha iyi başa çıkar, hatalar daha kolay görülür.

K11

Analiz iş akışındaki modeller (modelleme türleri) nelerdir?

Çözüm

Functional modeling (senaryolar), entity class modeling (sınıflar, nitelikler, ilişkiler: class diagram), dynamic modeling (her sınıfa yapılan işlemler, durum geçişleri: statechart).

K12

CRC kartı nedir, ne işe yarar, nasıl gösterilir?

Çözüm

Class–Responsibility–Collaboration: her sınıf için adı, sorumlulukları (ne yapar/bilir) ve işbirliği yaptığı sınıflar yazılır. Sınıfları bulmak (alan bilgisi gerekir) ve özellikle analiz artifact'larını test etmek için kullanılır; ekip kartları canlandırınca eksik/hatalı öğeler ortaya çıkar.

K13

Use case nedir? Include ve extends neyi ifade eder?

Çözüm

Use case, ürün ile aktörleri arasındaki etkileşimi modeller; sistem dikdörtgen, aktör çöp adam, use case elips. «include»: ana use case'in her seferinde kullandığı, yeniden kullanım için ayrılmış davranış (ok ana → kullanılan). «extend»: istisnai/nadir durumlar (ok istisna → ana).

K14

Distribute the control (dağıtık kontrol) nedir?

Çözüm

Bütün sorumluluğu tek sınıfa yüklemek (God class) yerine kontrolü dağıtmak: asansör probleminde her asansöre ve her kata bir alt kontrolcü ve bir zamanlayıcı (scheduler).

K15

Collaboration diagram nedir?

Çözüm

Bir senaryonun gerçekleştirilmesinde nesneleri, aralarındaki bağlantıları ve gönderilme sırasına göre numaralanmış mesajları gösteren interaction diagram; eşdeğeri sequence diagram'dır.

K16

Specification document nedir, önemi nedir?

Çözüm

Müşteri ile geliştirici arasında sözleşmedir; kesin olmalı, çelişki, eksiklik ve tamamlanmamışlık içermemeli. Test ve bakım için şarttır. Unified Process'te use case'ler ve onlardan türeyen UML artifact'ları bu rolü oynar (müşteri için metin, tasarımcı için diyagram).

K17

Gereksinimler kaç grupta toplanır?

Çözüm

Functional (ürünün yapması gereken eylemler; girdi–çıktı) ve nonfunctional (ürünün özellikleri: platform, yanıt süresi, güvenilirlik; bazıları tasarıma kadar bekler).

K18

CASE aracı nedir? Örnek veriniz.

Çözüm

Computer-Aided Software Engineering: UML diyagramlarını çizmek, değiştirmek, belgeleri saklamak ve süreci izlemek için yazılım araçları. IBM Rational Rose, Together, ArgoUML, System Architect.

K19

Sınıf türlerini yazarak açıklayınız.

Çözüm
  • Entity class: uzun ömürlü bilgiyi modeller (ör. müşteri, kitap, hesap); bilgi ürün kapanınca da saklanır. Stereotip «entity», simgesi altı çizili daire.
  • Boundary class: ürün ile aktörler (çevresi) arasındaki etkileşimi modeller; genelde girdi/çıktıyla ilgilidir (ekran, form, rapor, yazıcı). Stereotip «boundary», simgesi solunda dikey çizgi olan daire.
  • Control class: karmaşık hesaplamaları ve algoritmaları modeller; use case akışını yönetir (ör. ücret hesabı, kuralların kontrolü). Stereotip «control», simgesi üstünde ok olan daire.
K20

Information hiding nedir, neden ihtiyaç duyulur?

Çözüm

Değişmesi muhtemel ayrıntıların modülün içinde gizlenmesi; değişiklik yerelleşir, diğer modüller etkilenmez, regression azalır; kullanıcı kritik verileri doğrudan değiştiremez (en az yetki).

K21

Abstract data type ve abstraction nedir?

Çözüm

ADT: veri tipi + o tipin örnekleri üzerindeki işlemler (informational cohesion; sınıflar). Abstraction: gereksiz ayrıntıları gizleyip ilgili ayrıntıları vurgulayarak problemi daha üst düzeyde düşünmek (stepwise refinement aracı).

K22

Modül nedir? Bir modülün kaç özelliği vardır?

Çözüm

A lexically contiguous sequence of program statements, bounded by boundary elements, with an aggregate identifier.Sınır öğeleriyle çevrili, bir toplu tanımlayıcısı (ismi) olan, kodda bitişik program komutları dizisi. Üç özelliği: function (ne yapar), logic (nasıl yapar), context (ne üzerinde çalışır).

K23

Nesne yönelimli programlamanın bakımda sağladığı avantajlar nelerdir?

Çözüm

Information hiding sayesinde değişiklikler yerel kalır, regression azalır; bağımsız birimler (encapsulation) hatanın yerini bulmayı kolaylaştırır; yeniden kullanım; yüksek cohesion ve düşük coupling'li modüller.

K24

Dynamic binding nedir?

Çözüm

Hangi metodun çalışacağının nesnenin sınıfına göre çalışma zamanında belirlenmesi (myFile.open() örneği); polymorphism ile birlikte gelir. Güçlü yandır ama kodu anlamayı zorlaştırabilir.

K25

Görüşme türleri nelerdir? Görüşmeci nasıl olmalı?

Çözüm

Structured (önceden planlanmış, kapalı uçlu sorular) ve unstructured (cevaplara göre sorulan, açık uçlu sorular). Görüşmeci alanı iyi bilmeli, açık fikirli olmalı; görüşmeden sonra yazılı rapor hazırlayıp bir kopyasını görüşülen kişiye vermeli.

8Alıştırmalar: koddan cohesion ve coupling bulma

Neden bu bölüm?

Son iki vizede kod verilip tür ve düzeltme istendi, WhatsApp'ta da “kod örneği var mı” diye çok soruldu. Aşağıdaki kodlar sınav tarzındadır.

A1
void SistemKapat()
{
    log.Kapat();
    ekran.Temizle();
    yedek.Al();
}
Çözüm

Temporal cohesion: işlemler birbirinden bağımsız, yalnızca kapanış anında art arda yapıldıkları için bir aradadır. Düzeltme: her iş kendi sınıfında (Logger.Kapat(), Ekran.Temizle(), Yedekleyici.Al()); kapanışta çağıran bunları ayrı ayrı çağırır.

A2
void Hesapla(char islem, double a, double b)
{
    if (islem == '+') Console.WriteLine(a + b);
    else if (islem == '-') Console.WriteLine(a - b);
    else if (islem == '*') Console.WriteLine(a * b);
}
Çözüm

Logical cohesion; çağıranla control coupling (islem bir kontrol öğesi). Open-Closed ilkesi ihlali (yeni işlem için if eklenir). Düzeltme: double Topla(double a, double b), Cikar, Carp ayrı metotlar (functional, data coupling) ya da IIslem arayüzü ve her işlem için sınıf. (2025–26 finalinde aynı tip soru SOLID ile birlikte geldi.)

A3
class Ogrenci { public string No, Ad, Soyad, Sifre; public double Ortalama; }
bool BursAlirMi(Ogrenci o) { return o.Ortalama >= 3.0; }
Çözüm

BursAlirMi functional; çağıranla arasında stamp coupling (bütün kayıt, şifre dahil, gönderiliyor; yalnızca Ortalama kullanılıyor). Düzeltme: bool BursAlirMi(double ortalama) ⇒ data coupling.

A4
static class Durum { public static bool indirimVar; }
void KampanyaBaslat() { Durum.indirimVar = true; }
double FiyatHesapla(double f) { return Durum.indirimVar ? f * 0.9 : f; }
Çözüm

İki metot arasında common coupling (aynı global veriyi yazıp okuyorlar). Düzeltme: double FiyatHesapla(double f, double indirimOrani) (data coupling) ya da kampanya bilgisini ve fiyat hesabını bir Kampanya sınıfında kapsülle (information hiding).

A5
void NotGirVeOrtalamaGuncelle(Ogrenci o, int not)
{
    o.Notlar.Add(not);
    o.Ortalama = o.Notlar.Average();
}
Çözüm

Communicational cohesion: iki iş (not ekleme, ortalama güncelleme), prosedürle ilişkili ve aynı veri (o) üzerinde. Daha iyisi: Ogrenci sınıfına NotEkle(int) ve Ortalama() metotları (sınıf informational, metotlar functional).

A6
class Kuyruk
{
    private int[] d = new int[100]; private int bas, son;
    public void Ekle(int x) { d[son++] = x; }
    public int Cikar() { return d[bas++]; }
    public bool BosMu() { return bas == son; }
}
Çözüm

Informational cohesion: her işlemin kendi giriş noktası ve bağımsız kodu var, hepsi aynı (gizli) veri yapısı üzerinde; bir ADT örneği. Düzeltme gerekmez.
